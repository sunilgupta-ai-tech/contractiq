# Testing deployment: Vercel + Render + Neon + Qdrant Cloud + R2 (Phase 26)

A free setup for the testing phase. Production on AWS is described in
[deployment.md](deployment.md).

```
Browser ──► Vercel (Next.js frontend)
               │  HTTPS, Bearer token
               ▼
            Render web service "docunexa-api" (one container)
               ├─ FastAPI API
               └─ worker (OCR, embedding, analysis)
                    │            │              │              │
                    ▼            ▼              ▼              ▼
               Render Key     Neon          Qdrant Cloud   Cloudflare R2
               Value (Redis)  (PostgreSQL)  (vectors)      (uploaded files)
```

| Part | Service | Free tier |
|---|---|---|
| Frontend | Vercel Hobby | Free for non-commercial use; paid customers need Pro |
| API + worker | Render free web service | 512 MB RAM; sleeps after 15 min idle |
| Queue and caches | Render Key Value | 25 MB, not persisted (jobs are recovered from PostgreSQL) |
| Database | Neon | 0.5 GB |
| Vectors | Qdrant Cloud | 1 GB cluster |
| Files | Cloudflare R2 | 10 GB |
| AI | Gemini API | pay per use, with your key |

Why one container: Render's free plan has no background workers and no disk
shared between services, so the API and the worker run together
(`infrastructure/render/Dockerfile`, `start.sh`), and files go to R2.

## 1. Neon (PostgreSQL)

1. Create a project at neon.tech, region close to your users (e.g. Singapore).
2. **Connection details** → turn **off** "Connection pooling" → copy the
   connection string. The app needs the direct connection; the pooled one
   breaks its prepared statements.
3. Rewrite it for the app (keep it secret, never commit it):

   ```
   postgresql://USER:PASSWORD@HOST/neondb?sslmode=require
   → postgresql+asyncpg://USER:PASSWORD@HOST/neondb?ssl=require
   ```

Tables, the row-level-security role and policies are created automatically on
the first start (`alembic upgrade head` in `start.sh`).

## 2. Qdrant Cloud (vectors)

1. cloud.qdrant.io → create a **free cluster**.
2. Copy the cluster URL (`https://….cloud.qdrant.io:6333`) and create an API key.

The collection is created on the first start.

## 3. Cloudflare R2 (files)

1. Cloudflare dashboard → **R2** → create a bucket, e.g. `docunexa-files`.
2. **Manage R2 API tokens** → create a token with *Object Read & Write* for
   that bucket. Note the **Access Key ID**, **Secret Access Key** and the
   endpoint `https://<account-id>.r2.cloudflarestorage.com`.

Files are encrypted at rest by R2. The bucket stays private: downloads go
through the API, which checks access and writes the audit log.

## 4. Render (API + worker)

1. render.com → **New → Blueprint** → connect the GitHub repository. Render
   reads `render.yaml` (branch `phase-9-multimodal`).
2. Fill in the values it asks for:

   | Variable | Value |
   |---|---|
   | `CORS_ORIGINS` | the Vercel URL from step 5 (you can set it after step 5) |
   | `DATABASE_URL` | from step 1 |
   | `QDRANT_URL`, `QDRANT_API_KEY` | from step 2 |
   | `AWS_S3_ENDPOINT_URL`, `AWS_S3_BUCKET`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | from step 3 |
   | `GEMINI_API_KEY` | your Gemini key (a paid-tier key: free-tier requests may be used for training) |

   `JWT_SECRET_KEY` is generated by Render; Redis is wired automatically.
3. Deploy. The first build takes about 10 minutes. Check
   `https://docunexa-api.onrender.com/api/v1/health` → `"status": "ok"`.

## 5. Vercel (frontend)

1. vercel.com → **Add New → Project** → import the repository.
2. **Root Directory**: `frontend`. Framework: Next.js (detected).
3. **Environment Variables** (Production and Preview):

   | Variable | Value |
   |---|---|
   | `NEXT_PUBLIC_API_BASE_URL` | `https://docunexa-api.onrender.com` (your Render URL, no trailing slash) |
   | `NEXT_PUBLIC_USE_DEMO_DATA` | `false` |

4. **Settings → Git → Production Branch**: `phase-9-multimodal` (until it is
   merged into `main`).
5. Deploy, then put the Vercel URL into Render's `CORS_ORIGINS` (several URLs:
   comma-separated) and redeploy the Render service.

`NEXT_PUBLIC_*` values are built into the frontend: after changing them,
redeploy on Vercel.

## 6. First sign-in

Open the Vercel URL → **Create organization**. That account is the
organization's admin. For the platform console, create a super admin once from
the Render **Shell**:

```
cd /srv && python -m app.platform_admin create --email you@example.com --name "Your Name"
```

## Behaviour of the free plans

- **Cold start**: after 15 minutes without requests the Render service sleeps;
  the next request takes about a minute. If the first sign-in times out, try
  again. Documents queued while it slept are picked up when it wakes (the job
  recovery sweep, Phase 23).
- **Memory**: one document is processed at a time (`WORKER_MAX_JOBS=1`).
  Tested in a 512 MB container: about 310 MB idle and 345 MB while processing
  and answering. Very large scanned PDFs may need the next plan up.
- **Redis is not persisted**: a restart empties the queue and caches; queued
  work is requeued from PostgreSQL.
- **Costs**: only Gemini usage (see the Usage page), unless a free tier is
  exceeded.

## Settings added for this setup

| Setting | Default | Meaning |
|---|---|---|
| `AWS_S3_ENDPOINT_URL` | empty (AWS S3) | S3-compatible store such as R2; AWS encryption headers are then not sent |
| `WORKER_MAX_JOBS` | 4 | Documents one worker processes at once |
