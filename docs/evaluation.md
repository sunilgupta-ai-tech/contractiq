# Evaluation (Phase 12)

Measures the RAG pipeline on a golden dataset, so any change (model, prompt, chunking, reranker, guardrail threshold) can be judged by numbers instead of impressions, and regressions fail a build.

```text
golden dataset ──► ingest (parse → chunk → embed → index, throwaway collection + tenant)
                      │
      per question:   ├─ retrieval   hybrid search + rerank  → Recall/Hit@k, MRR, nDCG
                      ├─ answer      real /query path (fast | agent)
                      └─ score       facts, abstention, citations, groundedness, [LLM judge]
                      │
                      ▼
         report.json + report.md  ──►  regression gate vs baseline  ──►  exit 0 / 1
```

## Run it

```bash
make eval                                   # in the running stack, with the configured models
cd backend && python -m app.evaluation run  # or directly, with env pointing at Qdrant/Redis

python -m app.evaluation run --mode agent           # evaluate the LangGraph agent instead
python -m app.evaluation run --judge                # add LLM-as-judge scores
python -m app.evaluation run --baseline eval/baseline/report.json   # regression gate
python -m app.evaluation run --save-tenant <org-id> # also store an EvaluationRun row
```

Exit codes: `0` ok, `1` regression against the baseline, `2` the run failed (e.g. model unreachable). Each run indexes into its own `eval_<id>` collection under a random tenant id, and deletes the collection afterwards (`--keep-collection` to inspect it). Real tenants' data is never searched.

## The golden dataset

`backend/app/evaluation/datasets/sample_msa.json`: 23 answerable questions and 4 that the contract can't answer. They cover dates, renewal, service levels, payment, a fee **table**, data protection, termination, liability, indemnity and disputes. The contract is a synthetic Northwind/Contoso MSA generated by `app/evaluation/sample_contract.py`, so the set is reproducible and contains no client data.

```json
{"id": "renewal-notice", "document": "msa",
 "question": "How much notice is needed to stop the agreement from renewing?",
 "expected_answer": "Written notice at least ninety (90) days before the end of the term.",
 "facts": ["90|ninety"],
 "evidence": [{"clause": "3.1"}],
 "tags": ["renewal", "dates"]}
```

* **Evidence is located, not pinned.** `clause`, `page` and/or `text` (all given fields must match) identify the relevant chunks among *everything indexed*, so recall has a true denominator, and the dataset survives re-chunking. Chunk ids would not.
* **Facts** are what a correct answer must contain. `|` separates alternatives. Matching ignores case and thousands separators, and numbers match whole (`5` never matches `15`).
* **Unanswerable** examples (`"answerable": false`) must get a "not found" reply.
* A unit test re-parses and re-chunks the sample contract and checks that every example's evidence and facts are still findable. A parser or chunker change that breaks the dataset fails CI.

To add your own contracts, copy the file, use `"path": "contracts/x.pdf"` (relative to the dataset file) instead of `builder`, and write questions whose facts appear verbatim in the contract. Use real contracts only where their use for testing is permitted.

## Metrics

| Metric | Meaning |
|---|---|
| `retrieval.recall@k`, `hit@k` (k = 1, 3, 5, 10) | After reranking: share of relevant chunks found / questions with any relevant chunk in the top k |
| `retrieval.mrr`, `ndcg@5` | Rank quality after reranking |
| `retrieval.fused_recall@10`, `fused_mrr` | Before reranking; the difference shows what the reranker adds |
| `answer.accuracy` | Answerable questions whose answer contains every expected fact |
| `answer.fact_recall` | Mean share of expected facts found |
| `answer.false_abstention_rate` | Answerable questions answered "not found" |
| `answer.abstention_accuracy` | Unanswerable questions correctly answered "not found" |
| `citations.precision` | Share of citations that point at a relevant chunk |
| `citations.relevant_rate` | Answers citing at least one relevant chunk |
| `grounding.mean` | Mean Phase 11 groundedness of answered questions |
| `judge.score` | `--judge` only: correct = 1, partially = 0.5, incorrect = 0 |
| `latency.p50_ms`, `p95_ms` | Per-question answer latency |

Deterministic metrics are the gate: they are free and repeatable. The LLM judge complements them. It catches a right number attached to the wrong obligation, but costs a call per question and varies by judge model. The judge sees only the question, the reference and the answer, and its JSON verdict is validated.

## Grounding calibration

Every report includes the evidence for Phase 11's `GROUNDING_MODE`: for each candidate `GROUNDING_MIN_SCORE`, it shows how many answered questions `enforce` would withhold, split into correct and incorrect.

| Threshold | Withheld | Correct withheld | Incorrect withheld | Accuracy of shown |
|---|---|---|---|---|

Pick the highest threshold that withholds (almost) no correct answers. If even the lowest one withholds correct answers, keep `flag`. Re-check after changing the model or the answer prompt.

The first evaluation run already paid off. It showed that the groundedness check credited a citation written *after* the full stop ("…notice. [1]") to the next sentence, which made correctly cited answers look ungrounded. This is fixed in `evidence_validator.check_grounding`, with a regression test.

## Regression gate and baseline

The gated metrics (higher is better) are `retrieval.recall@5`, `retrieval.mrr`, `answer.accuracy`, `answer.fact_recall`, `answer.abstention_accuracy`, `citations.relevant_rate` and `grounding.mean`. `answer.false_abstention_rate` is gated too (lower is better). A change beyond `--max-drop` (default 0.05, absolute) fails the run. With 23 answerable questions, one question is about 4.3 points, so the default allows one flipped answer, not two.

1. On a known-good commit, with production models configured: `make eval-baseline`, then review `/tmp/eval-reports/report.md`.
2. Commit `backend/eval/baseline/report.json`.
3. When a change is *meant* to move the metrics (new model, prompt or chunker version), update the baseline in its own commit, with the before/after in the PR.

Where it runs:

* **CI (every PR):** `tests/integration/test_evaluation_flow.py` ingests and evaluates the sample set with fake models. It checks that the whole harness works, and the keyword-search floor (recall@10 ≥ 0.8), at no cost.
* **`.github/workflows/evaluation.yml`:** nightly and on demand, with Gemini (`GEMINI_API_KEY` secret). It gates against the committed baseline and uploads `report.md` / `report.json`.

## Reports

`report.json` holds the config snapshot, metrics, calibration and every example (retrieved chunk ids, answer, citations, scores, unsupported sentences). `report.md` is the reviewer's summary: metrics, calibration, failures and the gate result. The config snapshot records the model, embedding model, reranker, chunker and prompt versions, retrieval sizes, grounding settings and `GIT_SHA`, so a metric change can be attributed. `--save-tenant` also stores the run in `evaluation_runs`.
